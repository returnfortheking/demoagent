## 1. 项目背景与目标

### 1.1 为什么做这个项目

本项目同时服务两个目标：

**目标 A — 工作价值**
HiSpark Studio for VS Code 是面向海思芯片开发者的集成开发环境，覆盖代码编写、编译、烧录、调试全流程。当前开发者必须手动操作 GUI 按钮，需记忆大量配置参数。本项目为其注入 AI 能力，让开发者通过自然语言完成开发操作，并可随时查阅官方文档。

**目标 B — 技术学习**
通过一个真实项目，**演进式**地经历 LangChain 全技术栈的发展历史，覆盖大模型应用开发大厂面试中的全部高频考点（Q1–Q16），形成"可讲故事"的实战经验。

### 1.2 项目宗旨

> 以真实工作需求为驱动，在每一次"旧方案遇到瓶颈 → 升级新方案"的循环中，亲手实践 LangChain 演进史上的每个关键技术节点。

## 2. 功能需求

### 2.1 核心功能

| 功能模块 | 描述 |
|---------|------|
| **F1 自然语言操控** | 通过对话控制 HiSpark 的编译、烧录、SDK下载、栈/镜像分析等操作 |
| **F2 知识问答** | 基于官方文档的 RAG 问答，文档不足时自动联网补充 |
| **F3 自定义知识库** | 用户可上传自有文档（PDF/MD/TXT），系统自动索引后参与检索 |
| **F4 操作安全确认** | 烧录等不可逆操作执行前，必须通过 Human-in-the-loop 确认 |
| **F5 可观测性** | 全链路 Tracing（LangSmith），RAG 质量自动评估 |

### 2.2 非功能需求

- **响应时间**：普通问答 < 5s，命令执行类 < 3s（不含操作本身耗时）
- **可扩展性**：新增工具/文档不需修改 Agent 核心逻辑
- **可测试性**：每个模块有独立单元测试，TDD 开发
- **可移植性**：Backend 独立运行，不强依赖 VS Code（可通过 Gradio Web UI 单独使用）

### 3.2 关键设计决策

**决策 1：Python 是大脑，TypeScript 是手**

Agent 所有推理逻辑在 Python 中完成。当 Agent 决定执行 HiSpark 命令时，返回结构化动作对象而非直接执行：

```json
{
  "action": "vscode_command",
  "command": "hispark.build",
  "args": { "mode": "release", "target": "WS63" },
  "requires_confirmation": false
}
```

TypeScript Extension Host 接收后调用 `vscode.commands.executeCommand()`。这样：
- Python 后端可独立测试（不依赖 VS Code 环境）
- TypeScript 层薄且无业务逻辑，易于维护

**决策 2：危险操作走 HITL（Human-in-the-loop）**

烧录（`hispark.flash`）是不可逆操作。当 Agent 决定执行烧录时，LangGraph Checkpoint 暂停执行，返回确认请求给用户，用户确认后恢复执行。这直接对应面经 Q5。

**决策 3：知识库检索优先级**

```
用户问题 → 自定义KB检索 → 官方文档检索 → LLM判断是否充分
                                                ↓ 不充分
                                          联网搜索补充
                                                ↓
                                          融合后生成答案（标注来源）
```

**决策 4：演进式开发，每个版本独立 Git Tag**

每次升级都有明确的"痛点驱动"，见第 4 节。

### v0.1 — 旧版 LangChain（LLMChain + RetrievalQA）

**覆盖面经**: Q2（Chain vs Agent 对比起点）、Q3（RAG基础流程）、Q8（切块策略初探）、Q14（向量数据库选型）

**实现功能**:
- 基于 `LLMChain` 的 HiSpark 命令解析（自然语言→命令名）
- 基于 `RetrievalQA` 的官方文档问答（RAG 7步流程）
- 使用 `ConversationBufferMemory` 保持多轮对话
- Chroma 向量库 + `text-embedding-3-small`（或智谱 embedding）
- Gradio Web UI（快速验证）

**核心代码风格（旧版 API）**:
```python
# v0.1 风格 — 即将被 LCEL 取代的写法
from langchain.chains import LLMChain, RetrievalQA, ConversationalRetrievalChain
from langchain.memory import ConversationBufferMemory

llm = ChatZhipuAI(model="glm-4-flash")

# 旧版：各组件接口不统一，.run()/.predict()/.call() 混用
qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    retriever=vectorstore.as_retriever(),
    chain_type="stuff"
)
result = qa_chain.run(query)   # .run() — v0.2 后废弃
```

**本版本的已知痛点**（在 `docs/changelogs/v0.1.md` 中记录）:
- `LLMChain`、`RetrievalQA`、`ConversationalRetrievalChain` 接口不统一
- 不支持原生流式输出
- 难以组合多个链（SequentialChain 繁琐）
- 中间步骤不透明（不知道 LLM 看到了什么）
- Agent 无法动态决策（文档找不到时无法自动切换策略）

---

### v0.2 — 迁移到 LCEL

**覆盖面经**: Q1（LCEL核心语法、Runnable协议）、Q2（Chain定义明确化）

**迁移动作**:
- `LLMChain` → `prompt | llm | StrOutputParser()`
- `RetrievalQA` → LCEL RAG Chain（`retriever | format_docs | prompt | llm`）
- `ConversationalRetrievalChain` → `RunnableWithMessageHistory`
- 所有链统一用 `.invoke()` / `.stream()` / `.batch()`

**核心代码风格（LCEL）**:
```python
# v0.2 风格 — 声明式、流式、可组合
from langchain_core.runnables import RunnablePassthrough

rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)

# 流式输出（旧版 LLMChain 做不到）
for chunk in rag_chain.stream("WS63 支持哪些功能？"):
    print(chunk, end="", flush=True)
```

**Changelog 记录的升级理由**:
> "旧版 `RetrievalQA` 无法在流式场景中逐 token 返回，Gradio 界面卡顿。迁移到 LCEL 后，流式输出和链组合都变得自然。统一的 Runnable 接口让代码更容易理解和测试。"

---

### v0.3 — 接入 LangSmith

**覆盖面经**: Q6（Tracing配置与使用）、Q7（LLM-as-a-Judge）

**实现内容**:
- 配置 4 个环境变量开启 LangSmith Tracing
- `@traceable` 装饰器标记自定义函数
- 构建 RAG 评估数据集（10条 HiSpark 相关 QA 对）
- 实现 Faithfulness + Answer Relevancy 两个 LLM 评估器
- 对比 v0.1 和 v0.2 的评估得分（体验版本对比功能）

**Changelog 记录的升级理由**:
> "v0.2 上线后发现部分问题答非所问，但不知道是检索问题还是生成问题。接入 LangSmith 后，能清楚看到每次检索召回了哪些 chunk、LLM 看到的完整 Prompt 是什么，定位到是切块策略导致关键信息被截断。"

---

### v0.4 — 进阶 RAG（Chunking + 混合检索 + Reranker + RAGAS）

**覆盖面经**: Q8（切块策略）、Q9（召回优化/两阶段检索）、Q10（RAGAS评估）

**实现内容**:
- 对比 4 种切块策略：固定大小 / 滑动窗口 / 语义切分 / 结构化切分（按 MD 标题）
- 混合检索：BM25（`rank_bm25`）+ BGE 向量检索，RRF 融合
- BGE-Reranker Cross-Encoder 精排
- RAGAS 4指标评估（Context Recall/Precision, Faithfulness, Answer Relevancy）
- LangSmith 对比 v0.3 和 v0.4 的 RAGAS 得分

**Changelog 记录的升级理由**:
> "v0.3 的 RAGAS Context Recall 只有 0.6，分析发现：1）固定切块割裂了表格内容；2）语义检索对'BS25'这类专有名词效果差。改用结构化切分 + BM25混合检索后，Recall 提升到 0.85。"

---

### v0.5 — 升级到 LangGraph（Agentic RAG + ReAct）

**覆盖面经**: Q4（State/Node/Edge三要素）、Q11（Agentic RAG）、Q12（ReAct框架）

**升级动机（最重要的演进节点）**:
v0.4 的 LCEL Chain 是固定流程：检索→生成。但实际使用中遇到：
- 问题复杂时，一次检索不够，需要迭代检索
- 有时根本不需要检索（用户说"编译"，直接执行命令即可）
- Chain 无法动态决策"要不要检索"、"检索几次"

**实现内容**:
- 用 `StateGraph` 重建 Agent，定义 `AgentState`
- 实现 ReAct 循环（Thought → Action → Observation → Final Answer）
- 检索变成 Tool，LLM 自主决定是否调用、调用几次
- 支持"先尝试从文档回答，不足再联网搜索"的动态策略

**核心代码结构**:
```python
# v0.5 风格 — LangGraph StateGraph
class AgentState(TypedDict):
    messages: Annotated[list, operator.add]
    retrieved_docs: list
    iteration_count: int

graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)      # LLM 推理节点
graph.add_node("tools", tool_node)       # 工具执行节点
graph.add_conditional_edges("agent", should_continue, {...})
graph.add_edge("tools", "agent")         # ReAct 循环
```

### v0.6 — Checkpoint + Human-in-the-loop（烧录安全确认）

**覆盖面经**: Q5（HITL三步机制）、Q15（Checkpoint + thread_id）

**业务背景**:
用户通过对话触发烧录操作，一旦执行就写入设备 Flash，无法撤销。需要在执行前暂停，显示"即将烧录 COM3，确认吗？"，等用户确认后再执行。

**实现内容**:
- `MemorySaver` Checkpointer（开发期），`SqliteSaver`（生产期）
- `interrupt_before=["flash_confirm_node"]` 暂停烧录节点
- `graph.update_state()` 注入用户确认结果
- `graph.invoke(None, config)` 从断点恢复
- `thread_id` 区分不同开发者的会话（演示多用户隔离）

**Changelog 记录的升级理由**:
> "测试时意外触发了烧录命令，写坏了开发板。加入 HITL 后，危险操作会暂停等待确认，thread_id 确保 A 用户的确认不会影响 B 用户的流程。"

---

### v0.7 — Multi-Agent Supervisor（拆分专业 Agent）

**覆盖面经**: Q13（Supervisor多Agent模式 vs Subgraph模式）

**业务背景**:
随着工具增加（编译/烧录/SDK下载/栈分析/文档检索/联网搜索），单一 Agent 工具太多（>10个），决策质量下降，且不同类型任务的提示词需求不同。

**实现内容**:
- Supervisor Agent：分析用户意图，路由给专业 Agent
- DevOps Agent：专门处理编译/烧录/SDK 等操作命令
- Knowledge Agent：专门处理文档检索和知识问答
- Supervisor 收集子 Agent 结果，生成最终回复

**工具数量触发点演示**:
```python
# v0.6: 单一 Agent，10+ 工具，LLM 频繁选错工具
tools = [build, flash, download_sdk, stack_analysis, image_analysis,
         doc_retriever, web_searcher, kb_manager, monitor, debug, ...]

# v0.7: Supervisor 路由，每个 Agent 只有 3-4 个专属工具
devops_agent_tools = [build, flash, download_sdk, stack_analysis]
knowledge_agent_tools = [doc_retriever, web_searcher, kb_manager]
```

## 5. 技术栈

### 5.1 Python Backend

| 组件 | 选型 | 理由 |
|------|------|------|
| LLM | 智谱 GLM-4.7 / GLM-5 | 用户已有 Coding Plan Pro 订阅 |
| LLM 框架 | LangChain 0.3.x + LangGraph 0.2.x | 覆盖旧版到新版全演进 |
| Web 框架 | FastAPI + uvicorn | 支持 SSE 流式，异步性能好 |
| 向量数据库 | Chroma（开发） | 轻量，零配置，适合本地开发 |
| 嵌入模型 | BAAI/bge-small-zh-v1.5 | 中文效果好，可本地运行，无 API 费用 |
| 关键词检索 | rank_bm25 | BM25 标准实现，Python 纯库 |
| 精排模型 | BAAI/bge-reranker-v2-m3 | Cross-Encoder，中文效果优秀 |
| RAG 评估 | RAGAS 0.1.x | 标准 RAG 评估框架 |
| 开发期 UI | Gradio 4.x | 快速构建聊天界面，无需前端知识 |
| 测试 | pytest + pytest-asyncio | Python 标准测试框架 |
| 依赖管理 | uv + pyproject.toml | 现代 Python 包管理 |
| Tracing | LangSmith（可选） | 环境变量控制开关 |

### 5.2 TypeScript Extension（v0.8+）

| 组件 | 选型 | 理由 |
|------|------|------|
| 扩展框架 | VS Code Extension API | 必须 |
| 语言 | TypeScript | VS Code 扩展标准 |
| HTTP Client | node-fetch / axios | 调用 Python Backend |
| UI | Vanilla JS + CSS（Webview） | 轻量，避免打包复杂性 |
| 测试 | @vscode/test-electron + Mocha | VS Code 扩展标准测试框架 |

### 5.3 LLM 配置（智谱 GLM）

```python
# 智谱 API 兼容 OpenAI 接口，只需替换 base_url
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="glm-4-flash",           # 或 glm-4.7, glm-5
    openai_api_key="your_zhipu_api_key",
    openai_api_base="https://open.bigmodel.cn/api/paas/v4/",
    temperature=0.1,
)

# Embedding（智谱也提供 embedding API）
from langchain_openai import OpenAIEmbeddings
embeddings = OpenAIEmbeddings(
    model="embedding-3",
    openai_api_key="your_zhipu_api_key",
    openai_api_base="https://open.bigmodel.cn/api/paas/v4/",
)
```

> **注意**: 如果本地有 GPU 或 CPU 资源，也可用本地 BGE 嵌入模型，完全避免 Embedding API 费用。

## 7. 测试策略

### 7.1 TDD 流程（每个版本严格执行）

```
写测试（Red）→ 跑测试确认失败 → 写最少实现（Green）→ 重构（Refactor）→ 提交
```

**红灯验证**: 必须看到 `FAILED` 才能开始写实现代码
**绿灯验证**: 必须所有测试通过才能进入重构
**提交粒度**: 每个功能点独立提交，不允许"一次提交所有代码"

### 7.2 测试分层

| 层次 | 范围 | 工具 | 运行时机 |
|------|------|------|---------|
| 单元测试 | 单个函数/类 | pytest | 每次提交前 |
| 集成测试 | 多组件联合 | pytest + 真实 LLM | 每个版本完成时 |
| RAG 评估 | 检索+生成质量 | RAGAS + LangSmith | 每个版本完成时 |
| 端到端测试 | 完整用户流程 | pytest-e2e | v0.8+ |

### 7.3 测试覆盖目标

- 单元测试覆盖率：> 80%
- RAG 评估基线：v0.4 后 RAGAS 综合得分 > 0.75
- 每个版本有对应的评估报告（`docs/changelogs/vX.Y.md` 中包含）

## 9. 开发原则

- **TDD**: 先测试后实现，无例外
- **YAGNI**: 不为未来需求过度设计，每个版本只做够用的
- **DRY**: 抽象重复逻辑，但不为一次性代码创建抽象
- **频繁提交**: 每个功能点独立提交，保持 git log 可读
- **Changelog 驱动**: 每个版本的升级原因必须有文字记录，这就是面试素材
