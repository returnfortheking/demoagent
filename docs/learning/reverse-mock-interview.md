## Q1. 先介绍下这个项目，说下你觉得自己做得最好和最差的地方

这是为嵌入式开发插件 HiSpark Studio 配套的 AI Agent，让开发者可以用自然语言控制开发流程——比如"帮我编译 Hi3861 工程"或者"Wi-Fi 初始化怎么配置"，系统自动判断是执行命令还是检索文档。技术上是 Python FastAPI 加 LangChain 做后端，TypeScript VS Code Extension 做前端，SSE 做流式输出，目前完成了 v0.1 MVP 和 v0.2 LCEL 重构两个版本。

**最好的地方**是测试体系。三层分层测试——单元、集成、E2E——帮我发现了几个只有真实 VS Code 环境才能暴露的 bug，比如命令未注册时消息链路静默断裂，以及流式内容时序判断错误。

**最差的地方**是 v0.1 里为了让 mock 能跑通，在 src 目录下加了一个包装类。这污染了生产代码，后来专门制定规范禁止这类写法。这件事让我意识到，测试设计有问题时应该改测试，而不是改生产代码去迁就测试。

## Q2. 你遇到的最难解的问题是什么，你是怎样分析解决的，有什么启发

*（两个版本，可选其一作答）*

---

**版本 A：v0.2 RunnableWithMessageHistory 类型污染**

根因是一个框架的隐式行为：RunnableWithMessageHistory 配置了 input_messages_key 之后，会把传入的字符串自动包装成 HumanMessage 放进列表，这个列表会沿管道继续流动，最终流进了 retriever。Chroma 不认识列表，用它的字符串表示去做向量检索，自然匹配不到任何有意义的内容。

**现象**很迷惑：加上对话历史之后，RAG 检索质量断崖式下降，但单独测 retriever 和单独测历史功能都完全正常。我在 retriever 入口打日志，发现入参类型不对，从这里找到了根因。修复是在 retriever 之前插一个 RunnableLambda 做类型归一化。

**启发**：组件边界是隐式类型转换的高发地。遇到"分别正常、组合出错"，第一步应该打日志看边界处的实际数据，不要凭假设猜。框架帮你做的事越多，出问题时越难定位。

---

**版本 B：v0.1 E2E Webview 访问超时**

这个问题最终没有通过自己推断解决，而是通过一个关键实验打破了调试僵局。

**现象**：Playwright 能连上 VS Code 的调试端口，但始终无法访问 Webview 内部的 DOM，持续超时。调试过了十几次迭代都没有结果，方向越来越奇怪。

**转折点**：我做了一个简单实验——把 VS Code 完全关闭，重启后再跑，结果还是一样失败。这一个实验直接排除了当时主导的"进程锁状态异常"假设，因为重启应该能清掉任何运行时状态，但现象不变，说明根因是代码逻辑而不是环境状态。

**真正的根因**：Playwright 用 `Target.setAutoAttach` 命令追踪 OOPIF frame。这个命令对"尚未创建的 target"是可靠的——通过事件监听等它出现；但对"已经以独立进程形式运行的 OOPIF"，发现机制不可靠。固定等 5 秒，VS Code 完全启动后才连接，Webview OOPIF 已经独立运行，此时再发 setAutoAttach 找不到它。修复是改成重试连接，CDP 端口一开放就连上，此时 Webview 还没创建，setAutoAttach 能在它创建时捕获到事件，frame 引用就有了。

有意思的是，修复方案给出后，外部 AI 对根因的解释也是错的。我又做了五组控制变量实验，分别交叉测试"连接时机"和"frame 访问方式"两个变量，结果证明决定成败的只有连接时机，frame 访问方式完全不影响结果。

**启发**：调试要主动做反证，而不是只找支持当前假设的证据。一个简单的对照实验往往比十次代码迭代更有价值。另外，能跑通不代表解释是对的，有条件就用受控实验验证背后的原因。
