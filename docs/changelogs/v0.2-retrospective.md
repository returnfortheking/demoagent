## 一、开发前：计划歧义清理

### 背景

v0.2 开发计划写完后，发现存在多处歧义，必须在动代码前解决，否则开发到一半会被迫停下来重新设计。

**发现的歧义类型：**

| 类型 | 具体问题 | 决策 |
|------|---------|------|
| 歧义A：多文档交叉引用断链 | roadmap 里的 F 编号与 v0.2 plan 里的不一致 | 先修文档，再开发 |
| 歧义B：v0.2 新增 F30（真实文档入库）后 F 编号整体偏移 | F31-F81 全部需要 +1 | 写脚本批量替换 |

**经验：** 歧义本质上是"不同文档对同一个事实有不同描述"。找歧义的高效方法：从计划文档的每个接口签名出发，逐一核查它被哪些其他文档引用，是否一致。

## 二、Python 后端：LCEL 重构中遇到的问题

### 问题 1：RunnableWithMessageHistory 会把 question 包装成 [HumanMessage]

**这是 v0.2 最重要的 bug，值得反复讲清楚。**

**现象：** F16 实现完、单元测试全部通过，但集成测试报错：
```
TypeError: argument 'text': 'list' object cannot be converted to 'PyString'
```
错误发生在 tiktoken（token 计数库）里，调用栈指向 Chroma 的检索步骤。

**根因分析（三步推导）：**

第一步，看错误类型：`'list' object cannot be converted to 'PyString'`——某个地方把 list 传给了期望 str 的地方。

第二步，定位路径：检索步骤是 `itemgetter("question") | retriever`。`itemgetter("question")` 应该拿到字符串。但它实际拿到了什么？

第三步，查 `RunnableWithMessageHistory` 文档/源码：当设置了 `input_messages_key="question"` 时，框架在把 input dict 传给 base chain 之前，会把 `input["question"]` 的值——即字符串 `"帮我编译项目"`——**包装成** `[HumanMessage(content="帮我编译项目")]`。

这是框架设计的，目的是：把用户输入作为消息历史的一部分统一管理。

**结果：** base chain 里的 `itemgetter("question")` 拿到的是 `[HumanMessage("帮我编译项目")]`，而不是字符串。把这个 list 传给 `retriever`，retriever 交给 embedding 模型，embedding 模型调用 tiktoken 计数，tiktoken 崩了。

**解决方案：**
```python
from langchain_core.messages import BaseMessage
from langchain_core.runnables import RunnableLambda

def _to_question_str(x) -> str:
    """把 str | [HumanMessage] 两种形式都归一化为 str。"""
    if isinstance(x, list) and x:
        last = x[-1]
        return last.content if isinstance(last, BaseMessage) else str(last)
    if isinstance(x, BaseMessage):
        return x.content
    return str(x)

_to_str = RunnableLambda(_to_question_str)

# 在 base chain 里插入归一化步骤
base_chain = (
    {
        "context": itemgetter("question") | _to_str | retriever | _format_docs,
        "question": itemgetter("question") | _to_str,
    }
    | prompt | get_llm() | StrOutputParser()
)
```

**关键教训：**
> 使用 LangChain 高层封装（RunnableWithMessageHistory）时，要查清楚它对 input 做了什么"变换"，不要假设 input 原封不动传给 base chain。框架在管道的不同节点可能对数据做隐式变换。

**为什么单元测试没发现这个问题？**

因为单元测试 mock 了 `_get_qa_chain`，整个初始化和调用链都被绕过了，`_to_question_str` 的逻辑从未真正运行。这正是"Mock 是有意义的谎言"的反面：你在 mock 时假设"链会正确处理输入"，但实际链的数据流和你想象的不一样。

**分层测试的再认识：**
- 单元测试通过 → 代码逻辑正确
- 集成测试失败 → 框架与你的代码之间的"契约"理解有误
- 这两者失败的含义完全不同，需要不同的调试思路

### 问题 2：新增 session_id 参数破坏了现有集成测试

**现象：** F16 实现完，commit 时 gate 在 [5/8] 集成测试步骤失败：
```
TypeError: answer_question() missing 1 required positional argument: 'session_id'
```

**根因：** `answer_question(question: str)` 在 v0.2 重构后新增了必填参数 `session_id: str`。但 `tests/integration/test_llm_real.py` 里有 4 个调用点还用旧签名。

**修复方式：** 所有旧调用改为 `answer_question(question, session_id="integration-test")`。

**教训（YAGNI 的反面）：**
为了避免这类"忘了同步调用方"问题，Python 里有个最佳实践：

1. **工厂函数 + 关键字参数：** 用 `answer_question(question, *, session_id)` 强制调用方显式传 `session_id`（`*` 后的参数只能用关键字传）
2. **类型注解 + IDE：** 如果有 mypy 或 Pylance，签名变更会立即在调用处报错

v0.2 里没有用 mypy，所以依赖 gate 的集成测试来兜底——gate 在提交阶段就捕获了这个问题，没有进入主干，这正是 gate 的价值之一。

## 三、Python 后端：SSE 端点中遇到的问题

### 问题 3：`from ... import` 创建了局部绑定，导致 mock 失效

**现象：** F18 的单元测试场景1（answer 流式）在第一版实现里跑出了 37 个 delta 事件，而不是期望的 3 个。

**根因追查：**

`main.py` 的第一版实现：
```python
from src.chains.qa_chain import _get_qa_chain  # ❌

async def generate():
    chain = _get_qa_chain()  # 调用的是 local reference
    ...
```

测试里：
```python
mocker.patch("src.chains.qa_chain._get_qa_chain", return_value=mock_chain)  # patch 原始模块
```

**Python 的 import 机制：** `from module import name` 在调用方的命名空间里创建了一个**新的名称绑定**，指向被导入对象。之后对 `module.name` 的修改（patch）不会影响调用方已经持有的绑定。

等效于：
```python
# from src.chains.qa_chain import _get_qa_chain 等价于：
import src.chains.qa_chain
_get_qa_chain = src.chains.qa_chain._get_qa_chain  # 创建了副本

# 之后 patch src.chains.qa_chain._get_qa_chain ≠ patch 这个副本
```

**解决方案：通过模块引用访问**
```python
import src.chains.qa_chain as _qa_chain_module  # ✅

async def generate():
    chain = _qa_chain_module._get_qa_chain()  # 每次调用都走模块查找
    ...
```

`mocker.patch("src.chains.qa_chain._get_qa_chain", ...)` 修改的是 `src.chains.qa_chain` 这个模块对象的 `_get_qa_chain` 属性，当 `_qa_chain_module._get_qa_chain()` 执行时，它每次都通过模块对象查找属性，所以 patch 生效。

**这个原则在哪里都适用：**

> **Patch the reference the code actually uses, not where it was defined.**
>
> 如果被测代码用 `from X import Y` 把 Y 引入了自己的命名空间，就要 patch `your_module.Y`，而不是 `X.Y`。
>
> 如果被测代码通过 `import X` + `X.Y` 使用，patch `X.Y` 才生效。

这个原则在 v0.1 的 `intent_classifier` 测试里就用到了（mock `src.api.main.classify_intent`），v0.2 再次遇到，因为 `_get_qa_chain` 是私有工厂函数，没有被 re-export 到 `main.py` 的命名空间。

## 四、TypeScript 插件：流式显示中遇到的问题

### 问题 4：Playwright 流式测试读到了未完成的内容

**现象：** F19 第一版 E2E 测试失败：
```
AssertionError: Expected chip-related keyword in stream answer, got: "HiSpark Studio for"
```

**根因：** 代码逻辑是：
1. 等待 `#messages div` 的第 N 个元素出现（`.waitFor()`）
2. **立刻** 读取 `textContent()`
3. 断言文字包含关键词

但 `.waitFor()` 只等"元素存在于 DOM 中"，不等"元素的内容填充完毕"。SSE 流式场景下，第一个 token 到来就创建了 DOM 元素（`streamChunk` 事件），此时只有第一个 token 的文字。测试在第一个 token 渲染后立刻读值，断言自然失败。

**修复：等到流结束（status-bar 清空）再读内容**
```typescript
// ✅ 先等 streaming 完成
const deadline2 = Date.now() + 20000;
while (Date.now() < deadline2) {
    const sb = await activeFrame.locator('#status-bar').textContent() ?? '';
    if (!sb.trim()) { break; }  // status-bar 清空 = [DONE] 已收到
    await sleep(200);
}

// 再读最终内容
const streamText = await activeFrame.locator('#messages div').nth(divsBefore1).textContent() ?? '';
```

**设计反思：** 这是 E2E 流式测试中的经典陷阱——**异步 UI 更新的时序断言**。解决思路是：
- 不要 assert 中间状态的内容（streaming bubble 刚出现时）
- 要 assert 终止条件（`[DONE]` 已收到）之后的最终状态

`#status-bar` 清空是一个很好的"流式结束信号"——它与后端 `[DONE]` 事件直接关联（`streamDone` 消息处理函数清空了 status-bar），是测试可以可靠轮询的稳定信号。

### 问题 5：VS Code 命令执行失败导致 `actionDone` 永远不发出

**现象：** F19 流式 action 的 E2E 测试，等待 "已执行：编译项目" 气泡出现，但超时。

**根因分析：**

流程：
1. 后端 SSE 返回 `{type: "action", command: "hispark-studio.build", ...}`
2. `ChatPanel.sendMessageStream` 调用 `this._executor.handle(event)`
3. `executor.handle()` 调用 `vscode.commands.executeCommand('hispark-studio.build')`
4. E2E 测试环境中，`hispark-studio.build` 命令未注册 → Promise **reject**
5. `.then(() => postMessage({type: 'actionDone'}))` 在 reject 时**不执行**
6. `actionDone` 永远不发出，`#messages` 里不出现 "已执行" 气泡

**这里有一个设计权衡：**

选项A：不处理错误，`actionDone` 只在命令成功执行后发出（语义最准确）

选项B：用 `.finally()` 无论成功/失败都发出 `actionDone`（对 E2E 友好，但成功语义模糊）

**决策：选 `.finally()`，原因如下：**
1. v0.2 的目标是验证 SSE 流式架构是否通，命令执行的成功/失败是 v0.3+ 关注的问题
2. 在真实 HiSpark Studio 环境中，`hispark-studio.build` 是已注册命令，不会失败；失败只在测试环境发生
3. E2E 测试若因为命令未注册而无法验证 UI 流程，会降低测试的覆盖价值

```typescript
// ✅ 选择 finally：确保 UI 反馈不依赖命令执行成功
this._executor.handle(event as ChatResponse).finally(() => {
    void this._webviewPanel.webview.postMessage({
        type: 'actionDone',
        description,
    });
});
```

**面试话术：**
> "这里我做了一个显式权衡：`.then()` 语义上更准确（命令成功才反馈用户），`.finally()` 对 E2E 测试更友好（命令是否注册不影响 UI 流程验证）。我选了 `.finally()`，并在代码注释里说明原因——这个决策可以在 v0.3 用真实命令覆盖后重新评估。"

```

      VS Code + Playwright CDP，验证 Webview 渲染

  Mock 所有外部依赖，<2秒，每次开发后立即运行
```

### LCEL 对可测性的改善

v0.1 的 `_ChainWrapper`（为了绕过 Pydantic v2 的 `setattr` 限制）在 v0.2 完全消失了。原因：

LCEL 的 `RunnableLambda`、`ChatPromptTemplate` 等组件本身就是普通 Python 对象，不依赖 Pydantic `BaseModel`，pytest-mock 可以自由 patch `_get_qa_chain` 返回任意 `MagicMock`，不需要任何包装层。

**这是 LCEL 迁移的一个隐藏收益：** 不只是代码更简洁，也是测试更简单（没有包装类，没有 Pydantic 约束）。

### API 契约测试（F21）的价值

v0.2 新增了 `test_api_contract.py`，8 个测试覆盖：字段名、字段类型、HTTP 状态码、SSE 格式、[DONE] 终止标志。

**为什么单独写合约测试，E2E 测试不够用吗？**

E2E 测试验证的是"系统能工作"（端到端流程通），合约测试验证的是"接口形态稳定"（字段名不变、类型不变、格式不变）。

当你重构内部实现时（比如 v0.3 接入 LangSmith，链的实现变了），E2E 测试可能还能通（功能正常），但合约测试能保证接口没有悄悄变化（Extension 侧依赖 `requires_confirmation: bool`，如果它变成了字符串 `"true"`，E2E 可能还通，但 TypeScript 侧会崩）。

**合约测试是接口的"宪法"。**

## 六、架构决策记录

### 决策 1：SSE 而不是 WebSocket

**为什么选 Server-Sent Events（SSE），而不是 WebSocket？**

| 维度 | SSE | WebSocket |
|------|-----|-----------|
| 方向 | 单向（服务器→客户端） | 双向 |
| 实现复杂度 | 低（HTTP 长连接，`StreamingResponse`） | 高（需要握手、帧格式、连接管理） |
| LLM 流式输出场景 | 完全匹配 | 能用但过度设计 |
| 客户端读取 | HTTP 请求 + 流式读取 | 专用 WS 客户端 |
| 防火墙穿透 | 好（HTTP 协议） | 有时有问题（需要 WS 握手） |

LLM token 流式输出是典型的**单向推送**场景，SSE 是最合适的选择。WebSocket 是给需要双向实时通信（聊天室、协同编辑）的场景设计的。

**面试话术：**
> "流式输出我选了 SSE 而不是 WebSocket，因为 LLM token streaming 是单向推送，SSE 基于 HTTP 长连接，FastAPI 用 `StreamingResponse` 就能实现，客户端只需要 httpx 流式读取。WebSocket 虽然也能做，但它是双向协议，对这个场景来说是过度设计。"

---

### 决策 2：`sendMessageStream` 用 Node.js `http.request` 而不是 `fetch`

**背景：** Extension 里需要在 Node.js 环境（不是浏览器）读取 SSE 流。

**为什么不用 `fetch`？**
VS Code Extension 运行在 Electron 的 renderer process 里，技术上可以用 `fetch`。但 `fetch` 的 `ReadableStream` API 在 Node.js 里行为与浏览器略有差异，且需要 polyfill 处理兼容性。

**`http.request` 的优势：**
- Node.js 原生 API，无依赖
- 基于 `stream.Readable`，`res.on('data', chunk => ...)` 是经典流式消费模式
- Buffer 管理（跨 chunk 的不完整行）完全可控

**SSE 解析的 Buffer 管理：**
```typescript
let buffer = '';
res.on('data', (chunk: string) => {
    buffer += chunk;
    const lines = buffer.split('\n');
    buffer = lines.pop() ?? '';  // 最后一个可能是不完整的行，留到下次
    for (const line of lines) {
        if (!line.startsWith('data: ')) { continue; }
        // ...处理完整的 SSE 行
    }
});
```

这是处理流式数据时的标准技巧：**行缓冲（line buffering）**。网络包的边界不一定在行的边界，chunk 可能跨越多行，也可能在行中间截断。

### 决策 3：`streamingState.ts` 纯函数提取

**背景：** v0.2 Webview 侧新增了流式消息处理逻辑（statusUpdate、streamChunk、streamDone、actionDone）。

**问题：** 如果把这些逻辑写在 `chat.html` 的 `<script>` 里，就无法单元测试（HTML 里的 JS 无法 import，无法在 Node.js 环境运行）。

**解决方案：** 提取 `streamingState.ts` 纯函数模块

```typescript
// streamingState.ts — 纯函数，无 vscode 依赖，无 DOM 依赖
export function applyStreamEvent(state: StreamingState, event: {...}): StreamingState
```

这是 v0.1 `chatHtml.ts` 提取（把 HTML 生成从 ChatPanel.ts 分离）的同样模式，在 v0.2 再次应用：

> **可测试性原则（Testability Rule）：** 如果一段逻辑无法在普通 Node.js 进程里运行，把可测试的纯逻辑部分提取出来。VS Code API、DOM API、网络 I/O 都是"副作用边界"，纯逻辑可以从它们身上剥离。

测试结果：4 个单元测试，6ms 完成，不需要 VS Code，不需要浏览器。

## 九、v0.2 遗留问题（待 v0.3 修复）

### BUG-01：`stream-bubble` id 未清理导致流式气泡污染

**位置：** `extension/src/webview/chatHtml.ts` — `streamDone` 处理逻辑

**现象：**
`streamDone` 处理时只移除了 `stream-bubble` 的 `id` 属性，但如果 `streamDone` 消息丢失（如 Webview 重载、网络中断），`id="stream-bubble"` 会一直保留在 DOM 里。下一次流式请求进来时，`document.getElementById('stream-bubble')` 找到的是旧气泡，新 token 会追加到旧内容上，导致两次对话的内容混在一起。

**根因：** 流式完成检测依赖 `#status-bar` 隐式清空，`streamDone` 没有显式的 DOM 完成信号。

**修复方向：**
