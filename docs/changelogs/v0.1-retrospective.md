## 一、计划阶段的认知纠正

### 问题：第一版开发计划包含了完整的实现代码

**背景：** 在开始编码之前，AI 助手生成了一份详细的 v0.1 开发计划，计划里包含了每个模块的完整实现代码。

**用户反馈（原话）：**
> "你可以设计架构，设计接口定义，但我不推荐生成全部代码。你应该针对测试进行约束或详细设计，通过测试保证质量。现在的方案里测试代码是现成的，我认为并没有经过实际执行验证。"

**这个反馈揭示的问题：**
1. 预先生成的代码和测试从未真正"失败"过，TDD 的"红灯"阶段被跳过了
2. 计划里写好的测试代码反而限制了实现者的思考，变成了"抄代码"而不是"设计"
3. 测试场景表（输入/期望输出）远比预写代码更有价值——它描述"是什么"，而不是"怎么做"

**修正后的计划原则：**
- 计划只写：接口签名、Mock 目标、测试场景表（输入→期望输出）
- 不写：任何实现代码、测试代码
- 原因：TDD 的价值在于用失败的测试驱动实现，计划的职责是约束行为，不是预写答案

**面试话术：**
> "我在这个项目里实践了真正的 TDD——不是先写代码再补测试，而是先用测试场景表定义接口行为，每个 task 的第一步都是写测试并看到它失败，再去实现。这个流程强迫你在写任何代码之前就想清楚接口的边界条件。"

## 二、Python 后端：遇到的具体问题

### 问题 1：LangChain 版本陷阱——LLMChain 在 1.x 中被删除

**现象：**
```
ImportError: cannot import name 'LLMChain' from 'langchain'
```

**背景：** 项目 `pyproject.toml` 最初指定 `langchain>=1.0`，但 v0.1 设计上故意使用旧版 `LLMChain`（为了 v0.2 LCEL 重构时形成对比）。

**根因分析：**
LangChain 在 1.0 版本中彻底移除了 `LLMChain`，迁移到了 LCEL（LangChain Expression Language）。这是一次破坏性升级，不向下兼容。

**解决方案：**
```toml
langchain==0.3.25
langchain-openai==0.2.14
```
降级到 0.3.x 分支，该分支同时支持旧版 Chain 和 LCEL。

**更深的思考：**
这个"故意使用旧版"的设计决策本身值得解释。v0.1 用 `LLMChain`，v0.2 用 LCEL 重构，目的是在同一个项目里留下演进对比。面试中可以说："我见过很多教程只展示最新 API，但没有解释为什么要迁移、迁移了什么。我在这个项目里保留了旧实现，重构后可以直接对比代码，感受 LCEL 管道式设计（`prompt | llm | parser`）在可读性和可组合性上的优势。"

### 问题 2：Pydantic v2 与 pytest-mock 的不兼容

**现象：** 运行单元测试时，pytest-mock 的 teardown 阶段抛出异常：
```
AttributeError: __dict__
```
或者类似的 `delattr` 失败错误。

**根因分析：**
LangChain 0.3.x 的 `LLMChain`、`RetrievalQA` 等 Chain 对象都继承自 Pydantic v2 的 `BaseModel`，并且配置了 `model_config = ConfigDict(extra='forbid')`。

pytest-mock 的工作原理是：patch 一个对象的属性（`setattr`），测试结束后恢复（`delattr`）。但 Pydantic v2 的 `BaseModel` 不允许在实例上直接 `setattr`/`delattr`，因为字段是通过 `__slots__` 或验证器管控的。结果是：patch 能成功，但 teardown 时恢复操作失败。

**解决方案：`_ChainWrapper` 模式**
```python
class _ChainWrapper:
    """
    将 Pydantic v2 的 LangChain chain 对象包装在普通 Python 类里。
    目的：让 pytest-mock 可以 patch .run 方法（普通类支持 setattr/delattr）。
    """
    def __init__(self, chain):
        self._chain = chain

    def run(self, *args, **kwargs):
        return self._chain.run(*args, **kwargs)

_chain = _ChainWrapper(LLMChain(llm=get_llm(), prompt=_prompt))
```

Mock 目标从 `src.chains.intent_classifier._chain._chain.run` 变为 `src.chains.intent_classifier._chain.run`——包装器是普通 Python 类，pytest-mock 可以自由 patch。

**关键洞察：**
这个问题的本质是：**测试工具的假设（对象属性可以自由读写）与框架的约束（Pydantic 字段不可随意修改）之间的冲突**。解决方法不是绕过 Pydantic（那会破坏运行时安全性），也不是绕过 pytest-mock（那会让测试更复杂），而是在两者之间加一层薄薄的适配层。

**面试延伸：**
> 这个问题让我理解了为什么很多项目会在 LangChain 组件外面包一层自己的 wrapper class——不只是为了业务封装，也是为了让组件对测试工具更友好（testability）。

### 问题 3：模块导入时触发了 API 调用

**现象：** 运行 `pytest tests/unit/` 时，测试还没开始就消耗了 embedding API 额度，且如果没有网络就会失败。

**根因：**
`qa_chain.py` 的最初实现在模块级别初始化了 Chain 对象：
```python
# ❌ 问题写法：import 时立即调用 embedding API
retriever = build_retriever(_load_sample_docs())
_qa_chain = _ChainWrapper(RetrievalQA.from_chain_type(..., retriever=retriever))
```

**解决方案：懒加载（Lazy Initialization）**
```python
# ✅ 正确写法：第一次调用时才初始化
_qa_chain: Optional[_ChainWrapper] = None

def _get_qa_chain() -> _ChainWrapper:
    global _qa_chain
    if _qa_chain is None:
        retriever = build_retriever(_load_sample_docs())
        _qa_chain = _ChainWrapper(RetrievalQA.from_chain_type(..., retriever=retriever))
    return _qa_chain

def answer_question(question: str) -> str:
    return _get_qa_chain().run(question)
```

**Mock 目标也随之改变：**
原来 mock `_qa_chain.run`（直接 mock 实例的方法），现在 mock `_get_qa_chain`（mock 工厂函数，让它返回一个 MagicMock），这样初始化逻辑根本不会被触发。

**更广泛的原则：**
> 模块导入应该没有副作用（No Side Effects on Import）。API 调用、数据库连接、文件读取都不应该在 import 阶段发生。这是 Python 模块设计的基本原则，违反它会让测试变得脆弱，也会让应用启动时间不可预测。

### 问题 4：GLM 模型输出 Markdown 代码块包裹的 JSON

**现象：** 要求 LLM 输出 JSON，但实际收到：
```
```json
{"type": "action", "command": "hispark-studio.build"}
```
```

**根因：** GLM-4-Flash 在某些情况下会"友好地"给 JSON 加上 Markdown 代码块格式，这对人类阅读友好，但对程序解析是噪声。

**解决方案：** 在解析前 strip 代码块标记：
```python
def _strip_code_block(text: str) -> str:
    text = text.strip()
    if text.startswith("```"):
        lines = text.split("\n")
        # 去掉首行 (```json) 和尾行 (```)
        text = "\n".join(lines[1:-1] if lines[-1] == "```" else lines[1:])
    return text.strip()
```

**思考：**
这是一个典型的"LLM 输出不可信"问题。工程化 LLM 应用的核心挑战之一就是：**你无法控制 LLM 的输出格式，只能在解析层做防御**。更健壮的方案是使用 `output_parsers`（LangChain 内置）或 function calling / structured output（OpenAI/智谱 API 特性），v0.2 可以改进。

### 问题 5：RAG 测试只验证结构，没有验证答案质量

**背景：** F04 最初的单元测试只检查：
- `answer_question` 返回非 None
- 返回值是字符串
- 调用了一次 chain.run

用户提出问题（原话）：
> "task4的测试用例是否有关注RAG返回答案质量，是否有判断RAG返回答案的准确性？"

**这个问题的本质：**
结构性测试（返回了字符串）≠ 质量测试（返回了正确的字符串）。如果 RAG 检索到了错误的文档，或者向量化有问题，单元测试完全感知不到。

**解决方案：** 在集成测试中加入关键词断言
```python
@pytest.mark.integration
def test_rag_sdk_download_url():
    answer = answer_question("WS63的SDK从哪里下载？")
    # 不只检查非空，检查答案里包含正确的关键信息
    assert "gitee" in answer
    assert "fbb_ws63" in answer

@pytest.mark.integration
def test_rag_toolchain_env_variable():
    answer = answer_question("工具链安装完成后会添加什么环境变量？")
    assert "HISPARK_TOOL_PATH" in answer
```

同时把 `sample_docs.md` 从手工编造的占位符替换成真实的 HiSpark 文档内容。

**分层测试的洞察：**
- 单元测试的 Mock 是在撒谎——它假设 LLM 返回你期望的内容。这是必要的谎言（让测试快速、稳定），但需要集成测试来"解谎"
- 集成测试的价值不只是"验证 API 能通"，更重要的是**验证你的 Prompt 和检索策略在真实环境下有效**
- 关键词断言是 RAG 质量测试的最低门槛，v0.3/v0.4 可以升级为 LLM-as-a-Judge（用另一个 LLM 评分）

### 问题 6：.env.example 文件被意外写入了真实 API Key

**现象：** 在评估脚本运行过程中，`backend/.env.example` 文件里的 `ZHIPU_API_KEY=` 被填入了真实的 API Key。

**影响：** 如果直接提交，API Key 就会进入 git 历史，一旦推送到公开仓库就无法完全删除（git 历史永久保存）。

**处理方式：**
```bash
git checkout -- backend/.env.example  # 立即丢弃修改
```
在 commit 前检查 `git diff`，确认 .env.example 干净后再 commit。

**经验：**
- `.env` 文件（真实 key）永远不进 git，通过 `.gitignore` 屏蔽
- `.env.example`（模板，空 key）进 git，供他人参考格式
- 对任何包含凭据的文件提交前要 double-check

## 三、TypeScript 插件：遇到的具体问题

### 问题 7：getHtmlContent 依赖 vscode 模块，导致单元测试无法运行

**背景：** 最初 `ChatPanel.ts` 同时包含 Webview 管理逻辑和 HTML 生成逻辑，HTML 生成函数与 vscode API 在同一个文件里。

**问题：** 单元测试用 plain `node` 运行（不启动 VS Code），但只要 import `ChatPanel.ts`，就会 `require('vscode')`，而 vscode 模块只在 VS Code 进程内可用，plain node 里会报 `Cannot find module 'vscode'`。

**解决方案：** 将可测试的纯逻辑提取到独立文件
```
ChatPanel.ts     ← 依赖 vscode API（不可直接测试）
chatHtml.ts      ← 纯函数，无任何 import（可直接测试）
```

```typescript
// chatHtml.ts - 零依赖，可在任何环境运行
export function getHtmlContent(): string {
    return `<!DOCTYPE html>...`;
}
```

测试文件只 import `chatHtml.ts`，完全不触碰 vscode。

**设计原则体现：**
这是"将副作用推到边界"（Push side effects to the edges）的具体实践。纯函数（无 I/O、无外部依赖、相同输入相同输出）是最容易测试的代码单元，应该尽量提取出来。

### 问题 8：CommandExecutor 的依赖注入设计决策

**背景：** CommandExecutor 需要：
1. 执行 VS Code 命令：`vscode.commands.executeCommand(cmd)`
2. 显示确认对话框：`vscode.window.showWarningMessage(...)`

如果直接在 CommandExecutor 里调用这些 API，就必须在 VS Code 进程里才能运行，单元测试无法覆盖。

**设计决策：** 通过构造函数注入行为函数
```typescript
class CommandExecutor {
    constructor(
        private readonly executeFn: (cmd: string) => Promise<void>,
        private readonly confirmFn: (msg: string) => Promise<boolean>
    ) {}
    // ...
}
```

测试时注入 mock 函数：
```typescript
const executedCommands: string[] = [];
const executor = new CommandExecutor(
    async (cmd) => { executedCommands.push(cmd); },
    async (_msg) => true  // 总是确认
);
```

生产时注入真实 VS Code API：
```typescript
new CommandExecutor(
    async (cmd) => { await vscode.commands.executeCommand(cmd); },
    async (msg) => {
        const result = await vscode.window.showWarningMessage(msg, '确认', '取消');
        return result === '确认';
    }
)
```

**这是依赖注入（DI）的核心价值：** 不是为了"解耦"这个抽象概念，而是为了**在测试时替换掉那些难以控制的外部依赖**（UI 弹窗、系统命令、网络请求）。

**面试话术：**
> "TypeScript 插件侧我设计了一个 CommandExecutor，它通过构造函数接收执行函数和确认函数。这样测试时我传入 mock 函数，不需要启动 VS Code，5个测试用例覆盖了所有行为分支（直接执行/需要确认/用户取消/非action类型/确认消息内容），整个测试用例在 6ms 内完成。"

### 问题 9：VS Code Webview 缺少 CSP（Content Security Policy）

**背景：** 最初的 HTML 模板没有添加 Content-Security-Policy meta 标签。

**为什么这是问题：**
VS Code Webview 文档明确要求每个 Webview 必须有 CSP。原因是 Webview 是一个特权上下文（可以通过 postMessage 与 Extension Host 通信），如果没有 CSP，XSS 漏洞可能允许恶意脚本控制 Extension Host，进而执行任意 VS Code 命令。

**解决方案：**
```html
<meta http-equiv="Content-Security-Policy"
      content="default-src 'none'; script-src 'unsafe-inline';">
```

v0.1 使用 `'unsafe-inline'`（因为用了 inline script）。生产环境应升级为 nonce-based CSP：
```html
<meta http-equiv="Content-Security-Policy"
      content="default-src 'none'; script-src 'nonce-${nonce}';">
<script nonce="${nonce}">...</script>
```

**附带修复：** 同时加入了对 CSP 存在性的测试断言，确保后续修改不会意外删除它。

### 问题 10：TypeScript 类型系统——Thenable vs Promise

**现象：** 编译报错：
```
Argument of type '(cmd: string) => PromiseLike<void | undefined>'
is not assignable to parameter of type 'ExecuteFn'.
  Type 'PromiseLike<void | undefined>' is missing the following properties
  from type 'Promise<void>': catch, finally, [Symbol.toStringTag]
```

**根因：** VS Code API 返回 `Thenable<T>`（更宽泛的类型），不是标准的 `Promise<T>`。而 `ExecuteFn` 类型要求返回 `Promise<void>`。

**解决方案：** 用 `async` 函数包装，强制返回 `Promise<void>`：
```typescript
// ❌ 返回 PromiseLike，不符合 ExecuteFn
(cmd: string) => vscode.commands.executeCommand(cmd).then(() => undefined)

// ✅ async 函数总是返回 Promise
async (cmd: string) => { await vscode.commands.executeCommand(cmd); }
```

**洞察：** VS Code 使用 Thenable 而非 Promise 是历史原因（支持早期 TypeScript）。现代代码应该用 `async/await` 包装，既解决了类型问题，也让代码更易读。

## 四、测试策略的整体思考

### 测试金字塔在本项目的体现

```
        [E2E 测试] 5个
      全链路：uvicorn subprocess + 真实 LLM
      运行时间：~30秒，按版本运行一次

      [集成测试] 9个
    真实 LLM + 真实 Embedding，验证 Prompt 有效性
    运行时间：~26秒，每 task 完成后运行一次

    [单元测试] 25个 (Python 13 + TypeScript 12)
  Mock 所有外部依赖，测试纯逻辑
  运行时间：~2秒，每次提交前必须通过
```

### Mock 的本质是"有意义的谎言"

单元测试里，我们 mock 了 LLM 的返回值。这意味着：
- 单元测试不能告诉你 Prompt 是否有效
- 单元测试不能告诉你 RAG 的检索质量是否合格
- 单元测试只能告诉你：**假设 LLM 返回了 X，代码的处理逻辑是否正确**

这个假设必须由集成测试来验证。集成测试是 Mock 假设的"担保人"。

### 为什么 RAG 的集成测试要用关键词断言而不是精确匹配

```python
# ❌ 精确匹配：脆弱，LLM 每次措辞略不同就会失败
assert answer == "WS63 的 SDK 下载地址是 https://gitee.com/..."

# ✅ 关键词断言：稳健，验证核心事实而非措辞
assert "gitee" in answer
assert "fbb_ws63" in answer
```

LLM 生成的文本不是确定性的，每次调用的措辞可能不同，但核心事实（URL、变量名、关键词）应该稳定出现。这是 RAG 测试的基本策略。

## 六、一个架构决策：为什么先做 Python 后端，而不是先做 Extension

**直觉上的选择：** VS Code Extension 是面向用户的，先做 UI 好像更自然。

**实际的选择：** 先完成 Python 后端（F01-F06），再做 Extension（F07-F11）。

**原因：**
1. **验证核心假设：** 项目的核心技术难点是"LLM 能否准确分类意图"，这个假设必须先验证。Gradio UI（F06）让我们在不开发插件的情况下就能交互式测试后端
2. **降低返工风险：** 如果先做 Extension 再做后端，API 格式变化会导致 TypeScript 代码大量修改
3. **后端是合约，Extension 是消费者：** FastAPI 的 `/chat` 接口定义了数据格式，Extension 按格式消费。先稳定合约，再实现消费者

这种"由内而外"（Inside-Out）的开发顺序，与"由外而内"（Outside-In / BDD）形成对比。本项目选择了 Inside-Out，因为核心不确定性在后端的 LLM 行为，而不是 UI 交互。

## 七、关于 YAGNI 的几次决策

**YAGNI（You Aren't Gonna Need It）** 在本项目中被多次显式应用：

| 场景 | 被拒绝的"改进" | 拒绝原因 |
|------|--------------|---------|
| FastAPI 没有认证鉴权 | 加 JWT Auth | v0.1 是本地开发工具，无需认证 |
| RAG 用内存 Chroma | 接 PostgreSQL/持久化 | v0.1 只需验证 RAG 能否工作 |
| parseResponse 没有字段验证 | 加完整的运行时类型校验 | v0.1 后端是受控的，格式已知 |
| Webview CSP 用 unsafe-inline | 实现 nonce 生成 | v0.1 不发布到插件市场，unsafe-inline 可接受 |
| eval 脚本没有并发控制 | 加速批量评估 | 20 条用例，串行即可，速度不是问题 |

**核心判断标准：** "这个改进是现在的问题，还是假想的未来问题？"如果是后者，先记录下来，等真正遇到再解决。

## 八、版本演进路线（v0.1 之后的规划）

| 版本 | 核心改进 | 对比基准 |
|------|---------|---------|
