## 1. 项目背景与目标

### 1.1 为什么做这个项目

**目标 A — 工作价值**

HiSpark Studio for VS Code 是面向海思芯片开发者的集成开发环境，覆盖代码编写、编译、烧录、调试全流程。本项目为其注入 AI 能力，让开发者通过自然语言完成开发操作，并可随时查阅官方文档。

**目标 B — 技术学习**

通过一个真实项目，**演进式**地经历 LangChain 全技术栈的发展历史，覆盖大模型应用开发大厂面试中的全部高频考点（Q1–Q16），形成可讲述的实战经验。

### 1.2 项目宗旨

> 以真实工作需求为驱动，在每一次"旧方案 → 升级方案"的循环中，亲手实践 LangChain 演进史上的每个关键技术节点。**问题不在设计阶段预设，通过充分的测试和评估自然发现。**

## 2. 功能需求

### 2.1 核心功能

| ID | 功能模块 | 描述 |
|----|---------|------|
| F1 | 自然语言操控 | 通过对话控制 HiSpark 的编译、烧录、SDK下载、栈/镜像分析等操作 |
| F2 | 知识问答 | 基于官方文档的 RAG 问答，文档不足时自动联网补充 |
| F3 | 自定义知识库 | 用户可上传文档（PDF/MD/TXT），系统自动索引后参与检索 |
| F4 | 操作安全确认 | 不可逆操作（如烧录）执行前通过 Human-in-the-loop 确认 |
| F5 | 可观测性 | 全链路 Tracing（LangSmith），RAG 质量自动评估 |
| F6 | MCP 集成 | Agent 作为 MCP Client 调用工具；HiSpark Extension 作为 MCP Server |

### 2.2 非功能需求

- **可测试性**: 每个模块有独立单元测试，TDD 开发，每个版本有集成测试
- **可观测性**: v0.3 起接入 LangSmith，所有版本的 RAG 质量可量化对比
- **可移植性**: Python Backend 可独立运行（Gradio UI），不强依赖 VS Code

### 3.2 关键设计决策

**决策 1：Python 是大脑，TypeScript 是手**

Agent 所有推理在 Python 中完成。执行 HiSpark 命令时，返回结构化动作对象：

```json
{
  "action": "vscode_command",
  "command": "hispark.build",
  "args": { "mode": "release", "target": "WS63" },
  "requires_confirmation": false
}
```

TypeScript Extension Host 接收后调用 `vscode.commands.executeCommand()`。

**决策 2：危险操作走 HITL**

烧录等不可逆操作，通过 LangGraph Checkpoint 暂停，用户确认后恢复执行。

**决策 3：MCP 双角色（v0.8）**

- Python Agent 作为 **MCP Client**：先接入社区 MCP Server（filesystem/web-search），体验客户端协议细节
- HiSpark Extension 实现 **MCP Server**：将 hispark.build 等命令暴露为 MCP Tools，Agent 通过 MCP 协议发现并调用

**决策 4：双轨并行开发**

Extension 从 v0.1 起同步开发（最简骨架），Python 和 TypeScript 各自演进，每个版本包含集成测试验证两侧协作正确。

#### v0.1 — 旧版 LangChain + Extension 骨架

**Python Backend 功能**

- `LLMChain`：解析用户意图，识别 HiSpark 命令名和参数
- `RecursiveCharacterTextSplitter`：切分 HiSpark 官方文档
- `Chroma`：向量存储（内存模式）
- `RetrievalQA`：文档问答链
- `ConversationBufferMemory`：多轮对话记忆
- Gradio Web UI：独立于 Extension 的调试界面

**TypeScript Extension 功能**

- `package.json`：扩展清单，注册 `hisparkAgent.openChat` 命令
- `extension.ts`：`activate()` 入口，创建 WebviewPanel
- Webview HTML：最简聊天框（输入框 + 发送按钮 + 消息列表）
- Extension Host ↔ Webview：`postMessage` 消息通道
- Extension Host ↔ Backend：`fetch` 调用 `POST /chat`（非流式）
- **命令执行器**：解析 Backend 返回的结构化动作，调用 `vscode.commands.executeCommand()`

**接口契约（Python ↔ TypeScript）**

```
POST /chat
Request:  { "message": string, "thread_id": string }
Response: {
  "type": "answer" | "action",
  // type=answer：知识问答响应
  "answer"?: string,
  "sources"?: string[],
  // type=action：命令执行响应
  "command"?: string,          // e.g. "hispark.build"
  "args"?: object,             // e.g. { "mode": "release" }
  "requires_confirmation"?: boolean,
  "description"?: string       // 向用户展示的操作说明
}
```

Extension Host 收到 `type=action` 时，调用 `vscode.commands.executeCommand(command, args)`；收到 `type=answer` 时，在 Webview 展示文本。

#### v0.5 — LangGraph（State/Node/Edge + Agentic RAG + ReAct）

**Python Backend**

- `StateGraph` 重建 Agent：
  ```python
  class AgentState(TypedDict):
      messages: Annotated[list, operator.add]
      retrieved_docs: list[Document]
      iteration_count: int
  ```
- 条件边：有工具调用 → tools 节点；无 → END
- 检索作为 Tool，LLM 自主决定是否调用、调用几次
- 最大迭代次数限制，防止无限循环
- **web_searcher Tool**（首次引入）：文档检索不足时，LLM 自主决定是否联网搜索

**TypeScript Extension**

- 展示 Agent 推理过程（Thought/Action/Observation 逐步显示）
- 区分"正在检索..."和"正在生成..."两种 loading 状态

## 5. 测试架构

### 5.1 测试分层

```
┌────────────────────────────────────────────────────┐
│            集成测试（每个版本）                     │
│  Python Backend ↔ TypeScript Extension 端到端验证   │
├───────────────────┬────────────────────────────────┤

├───────────────────┼────────────────────────────────┤

│  单个函数/类      │  单个 TS 模块                   │
└───────────────────┴────────────────────────────────┘
```

### 5.2 跨栈集成测试策略

Python 和 TypeScript 之间通过 HTTP API 通信，集成测试采用以下方式：

**API 契约测试**：定义 OpenAPI Spec（`docs/api-spec.yaml`），Python 测试验证 Server 实现符合 spec，TypeScript 测试验证 Client 调用符合 spec。双方独立测试，通过 spec 对齐。

**E2E 测试**：启动真实 FastAPI 服务器，用 Python `httpx` 客户端模拟 Extension 行为，验证完整业务流程（不启动 VS Code 环境）。

**VS Code Extension 测试**：使用 `@vscode/test-electron` 在真实 VS Code 进程中运行，测试 Webview 消息通道、命令执行、文件系统访问等 VS Code 特有行为。

### 5.3 RAG 评估体系

**评估数据集（项目开始前一次性创建，后续所有版本复用）**

```
docs/evaluation/dataset.json
├── 20 条操作类 QA（自然语言描述 + 期望的 HiSpark 命令名 + 期望参数）
└── 20 条文档类 QA（问题 + 参考答案，来自 HiSpark 官方文档）
```

**评估方法演进**（三个阶段，各版本使用对应阶段的方法）

| 版本 | 评估方法 | 操作类指标 | 文档类指标 |
|------|---------|-----------|-----------|
| v0.1 | 人工标注 | 命令准确率（command 字段匹配） | 关键信息覆盖率（人工 Yes/No） |
| v0.3 | LLM-as-a-Judge | 命令准确率 | Faithfulness + Answer Relevancy |
| v0.4+ | RAGAS 框架 | 命令准确率 | Context Recall/Precision + Faithfulness + Answer Relevancy |

**每个版本产出**
```
docs/evaluation/
├── v01_baseline.json           # 人工标注基线
├── v03_llm_judge_report.json   # LLM 评估器结果
├── v04_strategy_comparison.json # 切块 × 检索策略矩阵（RAGAS）

└── v07_multiagent_vs_single.json
```

**原则：评估结果只记录事实，不在设计阶段预设结论。**

## 9. 开发原则

- **测试驱动**: 先写测试看红灯，再写实现看绿灯
- **结论由测试产生**: 评估结果记录事实，不在设计阶段预设
- **YAGNI**: 每个版本只实现当前版本需要的功能
- **频繁提交**: 每个功能点独立 commit，保持 git log 可读
- **Changelog 事后记录**: 版本 changelog 在开发完成后根据实际情况填写，不预写
